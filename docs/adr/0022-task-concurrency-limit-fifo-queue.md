# 任务并发上限：达到上限 FIFO 排队而非拒绝，占坑含等待用户交互

任务可无限并行：desktop 主进程 `beginExecution` 无全局闸门，N 个任务可同时流式执行，而用户需要限制同时消耗资源的任务数并放进设置页。决定新增全局任务并发上限（1-8，默认 3），并入执行设置（agent-settings.json 扩展）；达到上限时新任务的首条执行进入应用级 FIFO 任务排队，有空位自动开跑，而非拒绝发送。占坑口径为「名额从执行开始占到执行结束」：一次执行中途等待审批/问答（waiting-user）期间名额不释放。排队状态随任务持久化，重启后按序自动开跑；设置调大立即补跑排队任务，调小不中断运行中的。子代理并发上限（1-8 默认 3）是任务内机制，与本决策无关。

## 关键边界

- 消费点在 desktop 主进程的发送闸门（`task-ipc` 的 `deliverMessage`/`beginExecution` 一带），不在 agent-core——agent-core 无全局任务并发概念，也不为其新增；这与执行设置其余六项「resolver 注入 agent-core」的路径不同，本项由 desktop 侧直接消费，但共用同一 store、IPC 与设置页分区。
- 任务排队与输入队列（ADR 0013）是两个机制：输入队列是任务内的消息级排队，任务排队是应用级的任务首条执行排队；排队任务在输入队列语义上视同「忙」——排队期间再发的消息进入该任务的输入队列，开跑后按序发出，完全复用既有机制。
- 排队只针对首条执行：任务记录照常创建（侧栏可见），首条消息照常在消息流可见；中断排队任务即出队回空闲，已发消息保留。
- 「调大立即补跑」与 ADR 0017 的「已开始的执行用开始时的值」不冲突：补跑的是尚未开始执行的任务，执行参数快照语义不受影响。
- 升级即行为变化：现状无限并行，上线后默认 3，第 4 个任务会排队——这正是需求本意，属预期变化。

## 取舍

拒绝「达到上限拒绝发送并提示」：实现最小，但与输入队列「忙时排队、空闲自动发出」、子代理「超限 FIFO 排队」两处既有哲学不一致，且用户需手工重试。拒绝「等待用户交互不占坑」：名额释放后恢复执行须重新申请——等审批的任务在批准后可能要排队等其他任务结束才能继续，语义反直觉，恢复路径也要过闸门；且等待交互的任务执行上下文仍存活、随时恢复消耗资源，占坑语义诚实；堵坑问题由调大上限或中断任务解决。拒绝「重启后保持排队不自动开跑」：与输入队列「跨重启保留、空闲后自动发出」哲学不一致——排队任务的首条消息是用户已明确发出的指令，无人盯守自动开跑与既有机制同构。拒绝「新建独立 task-settings store」：执行设置分区 store/IPC/缓存/设置页四件套全复用，且「约束同时执行的任务数」可归入「约束 agent 执行行为的参数」外延（GLOSSARY「执行设置」词条已点名）；「谁消费归谁目录」的纯粹性让位于结构最省。不做「不限」档：想要宽松就设 8，`0 = 不限` 多一个分支语义。

影响面：desktop 主进程新增全局排队闸门与补跑泵、任务排队状态持久化，agent-settings 扩展并发上限字段与校验；ui 侧栏新增「排队中」徽章（`TaskActivity` 加 `queued` 态）、任务内排队状态条、执行设置分区新输入项；GLOSSARY 新增「任务并发上限」「任务排队」「排队任务」词条，「执行设置」词条点名新成员。
