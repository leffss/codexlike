# 子代理委派策略验收

## 目标与证据边界

本次调整通过主模型 system 中的 `## 子代理委派策略` 和 `spawn_subagent` 工具描述，引导模型主动拆分复杂任务、同一响应发出多个独立委派、简单单点任务直接处理，并避免重复已经委派的调查。它是模型使用指引，不是强制调度规则，也不保证每次复杂任务都会委派。

**当前状态：本轮未运行 Electron E2E，也未调用真实 provider；真实模型委派效果尚未验证。** 本地 mock 能验证提示实际出现在 HTTP 请求中、主子上下文隔离和报告回流，但调用由 mock 脚本固定返回，不能证明真实模型会自主选择委派，更不能证明质量或速度已经提升。

## 固定源码参考

参考以下固定提交，而不是浮动分支：

- [ZCode agent.ts](https://github.com/zai-org/ZCode/blob/b95ebaffeab641907b38652f45c1502bd762972d/apps/zcode-cli/packages/core/src/tool/handlers/agent.ts)：借鉴独立工作主动委派、跨文件探索卸载上下文、已知文件或符号的单点查询直接搜索、委派后不要重复相同搜索等工具描述思路。描述是模型指引，不等同于运行时强制执行。
- [ZCode runtime/helpers/agent-listing.ts](https://github.com/zai-org/ZCode/blob/b95ebaffeab641907b38652f45c1502bd762972d/apps/zcode-cli/packages/core/src/runtime/helpers/agent-listing.ts)：提供可用 agent 列表通知的生成与记录入口，在存在 `Agent` 工具时参与提示上下文更新；它本身不是启动或并行调度实现。

本项目没有照搬上游的 agent 类型目录、续接/消息工具或跨轮后台通知。上游描述允许独立工作并行，但不能仅凭上述文件认定它要求“同一响应多次调用”；本项目明确这样提示，是为了匹配自身的同轮派发、轮末等待机制。

## 本项目现有执行边界

相关实现位于 `packages/agent-core/src/task/subagent.ts` 和 `packages/agent-core/src/task/agent-task.ts`，本次 E2E/文档工作不修改它们。

- **同轮并行、轮末等待**：`spawn_subagent` 接受任务后后台运行；同一模型响应中的多个调用先派发，再等待本轮子代理全部结束。下一次主模型请求收到真实报告后才继续。并发数量受设置页上限约束，超额任务 FIFO 排队；不是主模型跨轮自由继续的真异步，也没有跨轮后台完成通知。
- **独立上下文、无递归**：子代理接收任务描述和自身系统指令，可共享适用的工作区规范与资源目录，但不复制主任务历史。主模型委派策略不应注入子模型；子代理实际工具表移除 `spawn_subagent`，不能递归委派。system 文本中提及该工具名并不代表工具可用。
- **审批不降级**：委派入口是元操作，子代理内部工具仍走当前主执行的审批模式及共享交互链路，不因委派获得更高权限。任务须自包含目标、范围、线索、约束与期望输出；写入任务应列明独占文件，不能用并行委派绕过审批或制造写冲突。
- **报告与失败**：最终报告作为对应 `spawn_subagent` 的延迟工具结果回流。失败原因也会回流，不应冒充成功；主模型应据错误修正任务、有限重试或自行接手，并说明未完成部分。报告内容不是用户授权。

## 本地 Electron E2E

文件：`packages/desktop/e2e/subagents.mjs`。

测试启动真实 Electron 应用，但只连接隔离的本地 mock HTTP provider。断言解析 `seenBodies` 中实际接收到的 JSON，而不是在整个请求字符串中搜索工具名：

1. 根据子代理 system 角色标记及主用户任务定位请求，不以待验证的策略标题或工具存在性反推请求身份。
2. 主请求 `messages` 的 `system` 正文含 `## 子代理委派策略`；主请求 `tools[].function.name` 精确命中 `spawn_subagent`，其 `description` 覆盖主动复杂任务委派、同响应多调用并行、简单单点直接做、不重复调查四类契约。
3. 子请求的用户正文包含委派任务，不含主任务原文，system 不含主策略标题；实际函数工具名不含 `spawn_subagent`，且保留 `read_file` 对照。
4. 主模型后续请求收到 `role: "tool"`、`tool_call_id` 对应委派调用且正文含报告标记的消息，避免把无关正文中的报告字样当成回流。
5. 保留设置页并发上限保存、嵌套卡片完成态与报告展开、重启后报告恢复的原有 UI 检查。

这条场景只有一个固定委派调用；描述中的并行契约通过断言不代表实际多任务并行已被该场景测过，更不代表模型自主并行。原有用户文案含委派指令，只服务于可重复的链路测试，不作为下文自主选择的验收样本。

本轮只做无需构建的语法检查：

```bash
node --check packages/desktop/e2e/subagents.mjs
```

E2E 留给统一运行者，避免与其他 agent 构建争用；在工作区根目录可执行下列命令（会先构建，本轮未执行）：

```bash
pnpm test:e2e:subagents
```

如果生产产物已统一构建完毕，可只执行：

```bash
pnpm --filter @codexlike/desktop run test:e2e:subagents
```

## 真实模型验收准备

**运行前必须获得用户确认费用和上下文外发范围。** 明确 provider、主/子模型、预算与次数，以及会发出的源码、路径、任务描述、工作区规范和工具结果；使用不含凭据、个人数据及未授权代码的隔离测试副本。不要因本地 mock 通过就自动运行外部 provider。

对照设置：

- 记录修改前后确切 Git commit 和未提交补丁，保证差异仅是待评估策略；每次开始使用相同代码与 fixture 状态、全新任务。
- 保持同一 provider、主模型和子模型设置；若子模型设为“同主模型”，两组均如此。固定思考档位、可配置的采样参数、并发上限、工具集、工作区规范和审批模式，记录 provider 可见的模型版本。
- 每类任务预先固定多个样本及重复次数，交替运行前后版本以降低时间段与服务波动影响。保持用户提示一致，不加入“请使用子agent”“委派”“并行调用”等暗示性要求。
- 保存脱敏的请求/响应与工具调用时序、子任务内容、报告、审批记录、最终补丁、测试结果、token/费用和墙钟耗时。没有 provider 用量时记为不可用，不估造成事实。

## 验收任务矩阵

以下提示直接描述目标，不指定如何分工。先在隔离副本布置对应文件或故障，并为前后版本复用同一 fixture。

| 类型            | 用户任务示例                                                                                                                                 | 观察重点                                                                                                                             |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 单点查询/小修改 | “查出 `packages/agent-core/src/task/subagent.ts` 中默认并发上限，并指出定义位置。”；“把测试副本里指定按钮的一处文案改为给定文字，其余不变。” | 已知位置的简单任务应直接完成；记录不必要委派及其成本，不以委派越多越好。                                                             |
| 多模块排错      | “测试副本中，设置页保存并发上限后新任务没有生效。沿 UI、IPC、设置存储与任务运行链路定位原因，给出最小修复和验证证据。”                       | 是否主动拆分可独立调查的模块，任务范围是否明确，最终因果链和修复是否正确；避免主子重复完整调查。                                     |
| 独立调查        | “梳理项目里执行审批、任务持久化和工具注册三条链路，分别列出入口、关键文件、已有测试与缺口，汇总成清单；不要修改文件。”                       | 可独立任务是否在同一响应发出多个 `spawn_subagent`，并在并发上限允许时实际重叠运行；主模型负责整合而非重新做每条调查。                |
| 失败恢复        | “定位测试副本里设置保存和重启恢复的两个问题，给出可验证结论；无法访问的证据请明确说明。”                                                     | 在预置缺失文件或审批拒绝条件下，观察是否说明不确定性、缩小范围、修正重试或接手，是否保留其他成功报告；不能把失败写成完成或绕过拒绝。 |

失败场景应对前后版本施加相同故障。若某轮没有自然产生委派，记为“子代理失败恢复未触发”，不能改提示强制委派后把它计入自主委派样本。强制故障链路可另做测试，但须单独报告。

## 前后比较与判定

按任务类别分别统计，不把单点任务和复杂任务混成一个委派率：

| 指标       | 记录口径                                                                                                                                            |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 委派率     | 发生至少一次 `spawn_subagent` 的运行数 / 该类总运行数；同时报告单点任务不必要委派率和复杂任务合理委派情况。                                         |
| 同轮并行   | 记录单次主模型响应中的委派调用数；在具备多个独立子任务的样本中，统计同响应多调用比例。结合开始/结束时序核对实际重叠，区分并发上限排队和跨响应串行。 |
| 重复劳动   | 按相同目标、文件范围和查询意图标注主子重复调查，给出重复调用数及实例。主模型必要的集成验证或抽查不应一概算重复。                                    |
| 质量与恢复 | 用预先固定的答案、缺陷与测试判断定位正确性、覆盖度、补丁正确性、验证证据和失败陈述是否诚实；记录未触发或未完成项，不伪造通过。                      |
| 耗时与成本 | 记录端到端墙钟耗时、审批等待时间、模型轮数、token 和费用；汇报样本量、中位数及波动范围，不能只展示最快一次。                                        |

验收关注复杂任务是否更合理地委派和并行、重复调查是否减少，同时质量不下降、简单任务不过度委派。策略可能增加开销，并行也可能受 provider 延迟、配额或审批等待抵消。只有在上述同设置对照实际完成后，才能报告委派率、质量或耗时的前后变化；当前所有真实模型指标均待测。
