# 目标模式（Goal Mode）规格

Status: ready-for-agent

## Problem Statement

现有任务是对话驱动的：每个回合都由用户消息触发，回合结束后任务回到空闲，跨回合自动续跑不存在。用户若想让 agent 完成一个需要多轮推进的长期目标（重构、迁移、修一批测试），必须不断手动发「继续」，或者依赖 `PLAN_USAGE_POLICY` 提示词条款在单回合内尽量推进——撞上单回合工具轮次上限就停了。缺一个「给一个目标，agent 自主跑到完成」的长期执行形态。

## Solution

引入**目标模式**（ADR 0035）：用户以 `/goal <目标>` 为任务设定一条持久目标，目标原文同时充当首条指令与完成判定标准；此后 agent 进入跨轮续跑循环——每轮正常回合结束后发起一次**完成判定**（无工具模型调用），未通过则携带判定反馈自动续跑下一轮，通过则目标完成。输入框上方提供目标进度行（暂停/恢复/编辑/清除）；用户消息进输入队列但激活期间不自动消费（暂停阀门）；token 预算与空转阻断两道护栏；重启恢复为暂停态。权限语义完全不变，可与任意审批模式组合。

## User Stories

1. 作为用户，我想用 `/goal <目标>` 为任务设定一个持久目标，这样 agent 能朝它自主连续工作而无需我逐条发消息。
2. 作为用户，我想让目标文本同时充当首条指令与完成标准，并在设定时被引导写清期望结果/约束/验证方式三要素，这样完成与否有明确判据。
3. 作为用户，我想在输入框上方看到目标进度行——目标摘要、状态、第 N 轮、累计时长，这样不翻消息流就知道进展。
4. 作为用户，我想随时暂停目标，这样需要补充信息或离开时能停住消耗。
5. 作为用户，我想恢复已暂停的目标，让它从暂停点继续续跑，累计账目保留。
6. 作为用户，我想通过进度行编辑目标文本，这样约束变化时不用推倒重来，逐轮验证历史仍保留。
7. 作为用户，我想清除目标，任务回到普通对话形态、输入队列恢复自动消费，历史验证记录随任务留痕。
8. 作为用户，我想让 Stop 按钮在目标激活时等价于暂停（可恢复），这样不需要区分两套停止语义。
9. 作为用户，我想在消息流看到每次判定的单行标记行（第 N 次迭代 · 验证中/已完成/未完成），这样能追踪每一轮验证结论。
10. 作为用户，判定未完成时我想在标记行看到下一步方向的一句摘要，这样知道 agent 接下来去哪。
11. 作为用户，续跑轮不产生用户气泡（内部输入），这样消息流诚实呈现谁在说话。
12. 作为用户，目标激活期间我发的消息进入输入队列排队但不自动发出，暂停或完成后逐条自动发出——补充指令不丢也不打断目标。
13. 作为用户，我想给目标设定 token 预算（任务用量口径：含主任务、子代理与压缩），超限后目标转为「预算受限」暂停而非继续消耗。
14. 作为用户，连续多轮判定未过且无实质工具活动时，我想让目标自动暂停为「未达成」并说明原因，而不是无限空转。
15. 作为用户，重启应用后进行中的目标恢复为「已暂停」态，由我手动恢复——不在我不知情时自动续跑消耗。
16. 作为用户，目标模式下（ask 档）照常收到审批请求，处理后目标继续——目标模式不改变权限语义。
17. 作为用户，我想在目标运行中照常使用工作计划（计划胶囊、步骤清单），计划与目标两层并存互不干扰。
18. 作为用户，目标激活期间 `/compact` 被禁用并提示先暂停（判定依赖完整历史），暂停期间照常可用。
19. 作为用户，我想在侧栏看到目标任务与普通执行中任务一致的运行口径（占任务并发上限一席、徽章一致），无需重新学习。
20. 作为用户，目标结束（已完成/未达成/预算受限/已清除）后任务回到空闲，输入队列自动开始发出排队消息。
21. 作为用户，目标与逐轮验证历史随任务落库，重启或中断后我能回看每轮判定结论与理由。
22. 作为用户，对话型（非任务型）目标能被判定直接通过，不至于为不适合拆轮推进的目标无限续跑。
23. 作为用户，判定请求自身故障（网络/坏输出）不把目标永久卡死、也不误报「未达成」（fail-open，不设独立用户态）。
24. 作为用户，我想在目标激活时照常切换审批模式（ask/assist/full-access），目标模式不扩权、不缩权。
25. 作为用户，配合任务自动批准或 full-access，目标任务可以长时间无人值守推进，过程完整落库可回看。
26. 作为用户，目标完成后任务保留全部过程内容（工作轮、标记行），可像普通任务一样归档与检索。

## Implementation Decisions

- **模块落位**（经用户确认）：
  - **agent-core**：目标实体与六态状态机、完成判定的模型调用与 prompt 构造、判定响应解析（JSON 容错）、续跑 prompt 构造、token 记账口径对接。纯 TS、零 Electron 依赖。
  - **desktop 宿主**：goal 编排器（回合结束的 idle 边界衔接续跑循环：发起判定 → 未过则发续跑输入）、输入队列互锁、`/goal` 斜杠命令解析与本地命令反馈、目标落库与重启恢复为暂停态、类型化 IPC 暴露目标状态与控制操作。落位先例：输入队列（跨回合编排住 desktop，agent-core 不知道宿主空闲语义）。
  - **ui**：目标进度行（输入框上方常驻）、判定标记行（消息流）、侧栏口径接线、胶囊条不动。
- **目标实体**：任务级字段（一任务至多一目标）；状态机六态：进行中（验证中为进度行副状态）/ 已暂停 / 已完成 / 未达成（连续 3 空转轮）/ 预算受限 / 已清除；逐轮验证记录（轮次、结论、理由、下一步方向、时间戳）与累计 token/时长随任务持久化。
- **完成判定契约**：一次独立模型请求——任务当前模型、无工具、输入 = 目标文本 + 完整消息历史，输出 `{passed, reason, nextAction}`；解析容忍代码围栏等包裹；判定 prompt 引导「对话型非任务目标直接 pass」「证据不足不通过」；判定自身故障 fail-open（具体偏向实现轮定），不设独立用户态。
- **续跑循环**：单轮 sendMessage 回合结束 → 目标进行中 → 发起判定 → 通过 → 已完成；未过 → 以内部输入（不产生用户气泡）发起下一轮；每轮判定后落一条消息流标记行。单回合工具轮次上限照旧适用（上限 200，goal 是回合间机制）。审批等待与对话内交互问答照旧（waiting-approval / waiting-user），处理完毕回到循环。
- **输入队列互锁**：目标「进行中」时队列 pump 不自动消费；转为已暂停/已完成/未达成/预算受限/已清除后恢复自动逐条发出。「等待用户交互期间输入框不可用」等既有规则不变。
- **护栏**：token 预算可选（复用任务用量账目口径，子代理用量计入），超限 → 预算受限暂停（可加预算或改目标后恢复）；空转判定 = 连续 3 轮判定未过且无实质工具活动 → 未达成暂停。预算与空转阈值的配置入口（执行设置 vs goal 级参数）实现轮定。
- **命令与控制面**：`/goal <目标>` 走斜杠命令体系（与 /new /compact 同族），成功/失败走本地命令反馈；进度行按钮：暂停/恢复/编辑/清除；Stop = 暂停。
- **重启与恢复**：目标状态随任务落库；重启后「进行中」目标恢复为「已暂停」（对照：残留 streaming 重置 idle 的既有恢复链路），由用户手动恢复；「已中断」未读提醒等口径沿用任务侧，不特判。
- **并发与归档**：目标激活任务在任务并发上限口径上视为持续执行、占一席；任务排队照旧；归档照旧。
- **`/compact` 边界**：目标进行中执行 `/compact` 给本地命令反馈提示「请先暂停目标」；暂停/终态期间照常可用。
- **领域语言**：GLOSSARY「目标 / 目标模式 / 完成判定」三词条与 ADR 0035 已落盘，实现与文案一律使用该词汇。

## Testing Decisions

- 好测试只断言外部行为（命令输入 → 目标状态 → 消息流/进度行呈现 → 队列与并发效果），不断言 prompt 逐字内容或内部函数结构。
- 四层接缝（全部现有，经用户确认）：
  1. **desktop e2e 场景**（最高接缝）：`/goal` 设定 → 原文消息 → 进度行 → 自动续跑 → 标记行 → 暂停/恢复 → 完成/护栏触发。前提：e2e stub provider 扩展「工作轮回复 + 判定回复」两条脚本化响应线。先例：mcp / work-plan 等场景脚本；合入前实跑（AGENTS.md 口径）。
  2. **agent-core 单测**（vitest + fake provider）：判定请求构造、响应解析容错、fail-open、续跑 prompt 构造、状态机转换、记账口径。先例：agent-task / approval 既有 fake provider 测试。
  3. **desktop 单测**：goal 编排器流转（idle 边界、判定→续跑/完成）、输入队列互锁与恢复消费、重启恢复为暂停、`/goal` 命令解析。先例：input-queue / task-queue 单测。
  4. **ui 单测**（jsdom）：进度行（状态·第 N 轮·时长·四按钮·空态）、标记行渲染与摘要。先例：process-pills-bar-ui。

## Out of Scope

- **steering**（运行中用户消息直接注入续跑轮）：留作后续演进，首版用暂停阀门。
- **迭代摘要卡**（ZCode 式逐轮 todo 摘要）：进度行 + 标记行已覆盖。
- **跨任务目标**（目标—任务两级实体、目标跨多任务推进）。
- **goal setup 访谈模式**（设定前的结构化访谈向导）；三要素引导以轻提示为限。
- **verifier 执行测试/命令**：完成判定是无工具模型自评；「跑测试证明完成」属于工作轮内 agent 自己的行为。
- **移动端/多端形态**。
- **预算耗尽通知、自动续预算**等运营类能力。

## Further Notes

- 参照物机制要点（供实现者参考，详见会话调研）：ZCode verifier 返回 `{passed, reason, nextAction}`、`nextAction` 充当下轮方向、判定基础设施失败 fail-open 防 卡死、预算超限 storage 态 `budget_limited` 阻塞队列消费；Codex 目标三要素写法（Outcome/Constraints/Verification）、进度行按钮组（pause/resume/edit/clear + 累计时长）、连续 3 空轮阻断、子代理 token 计入根预算。
- 实现轮遗留细节：fail-open 具体偏向、预算与空转阈值配置入口、判定 prompt 文案、目标文本长度上限（参照 4000 字符量级）、e2e stub 两线响应扩展方式。
- 拆票前按惯例把探索事实（agent-task 循环、input-queue pump、任务恢复链路、e2e stub 机制）沉淀到 `.scratch/goal-mode/notes.md`，各票以指针复用。
